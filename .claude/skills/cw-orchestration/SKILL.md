# `cw` — Multi-Session Orchestrator (Use It; Don't Reinvent It)

`cw` (claude-workspace) is the orchestration substrate for parallel and
autonomous Claude work: enqueue tickets, dispatch background workers, watch
them to terminal, triage the gates they park on, ship with auto-merge. When
work is dispatch-, parallel- or autonomous-shaped, reach for the cw primitive
first instead of hand-rolling a worse one.

- **Registered project** (in `~/.config/cw/clients.yaml`): drive it through cw.
- **Not registered**, but the work is cw-shaped: offer
  `cw init <name> --path <repo>` before hand-rolling. Do not silently fall back
  to shell glue.

Placeholders below: `<T>` is the ticket, `<C>` the client, `<lane>` a lane
name. Every command here is a plain single command, safe for the orchestrator
permission allowlist (no command substitution, loops or jq filters).

## Version

Written against cw 1.77.0. Run `cw --version`; if newer, trust `cw dev-queue show <T> -c <C>`'s `next:` over this list.

## State to command

`cw dev-queue show <T> -c <C>` is authoritative: its `next:` line lists the
commands that are legal for the row as it stands, and a human-kept gate is
labelled operator-only there. Read it first. This map says which of those
commands the orchestrator runs, when, and why. `cw dev-queue tasks -c <C>`
shows the first `next:` command per row in its NEXT column.

The CI/conflict HOLD entries below apply before approval or finalization guidance
in any other entry: a queue status or an older successful run does not establish
that the live PR head is clean. These are operator instructions, not runtime
switches or changes to automatic recipes.

- **`pending`**: Run `cw dev-queue wait <T> -c <C>` (in the background, only to sequence work) or `cw dev-queue cancel <T> -c <C>` when the ticket is verified satisfied or obsolete. Who: orchestrator. A pending row at a lane cap is correct, not a wedge.
- **`lane_paused` / `lane_circuit_paused`**: Run `cw lane resume <C> <lane>`. Who: orchestrator. A pending row whose lane is paused; read why the lane paused (a circuit breaker trips on consecutive spawn errors) before resuming it. Resume also resets the error counter.
- **`running`**: Run `cw dev-queue wait <T> -c <C>` (background, sequencing only) or `cw queue peek -c <C>` at a checkpoint. Who: orchestrator. A STOP row from peek is handled per `/cw-queue-peek`.
- **`completed` / `failed` / `cancelled`**: Run `cw dev-queue requeue <T> -c <C> --from-completed`, `cw dev-queue requeue <T> -c <C> --from-failed` or `cw dev-queue requeue <T> -c <C> --from-cancelled`, matching the row's status, after reading `show`. Who: orchestrator. A terminal row is re-entered only on evidence that the work is not done. A COMPLETED shipped row paged as `shipped_pr_checks_failed` is recovered with `cw dev-queue recover-red-pr <T> -c <C>` (it disarms auto-merge and regresses the row to impl with head-pinned feedback), not with `--from-completed`.
- **`ambiguities_pending_resolution` / `premises_pending_verification`**: Run `cw dev-queue resolve <T> -c <C> --file <decisions.md>` at the plan stage. Who: orchestrator. Answer only from the ticket's sources of truth (ticket body, plan-of-record, recorded decisions, linked RFCs, the code); a genuine product or scope fork those sources cannot answer still goes to the human. Outside the plan stage, `cw dev-queue requeue <T> -c <C>` only after a tracker delta (#1653). A second park on the same disposition goes to `/harden-ticket`.
- **`plan_pending_approval`**: Run `cw dev-queue approve <T> -c <C>` when the plan stays within the ticket's agreed scope. Who: orchestrator. When the plan is not yet quality-reviewed, approve may requeue it at the plan stage for Plan Quality Review instead of advancing (`plan_requeued` in the output); that is not an error. `cw dev-queue requeue <T> -c <C> --stage plan` re-runs the plan instead. Never `cw dev-queue add`: a re-add against a parked row is refused.
- **`review_pending_approval`**: Run `cw dev-queue approve <T> -c <C>`. Who: orchestrator. With signoff configured, approve re-routes the row to `awaiting_operator_signoff` instead of advancing; that park is the human's. `cw dev-queue requeue <T> -c <C> --stage review` re-runs review instead. At the terminal stage (finalize in the default pipeline) `approve` refuses, so `show` lists `cw dev-queue requeue <T> -c <C> --stage finalize` instead; run it only when `show` does not label the line `operator-only human gate`. A labelled line belongs to the operator-only entry below.
- **`plan_scope_drift`**: Run `cw dev-queue approve <T> -c <C> --scope-drift <paths>` when the growth is operator-directed or inside the agreed scope, otherwise `cw dev-queue requeue <T> -c <C>`. Who: orchestrator.
- **`codex_must_fix_findings`**: Adjudicate each finding via `/cw-followup`. Settle an out-of-scope or non-reproducible one with `cw review settle <file> --ticket <T> --reason "<why>" -c <C>`; send a real in-scope defect back with `cw dev-queue requeue <T> -c <C> --stage impl --regress`. To ship as-is once every finding is settled, run `cw dev-queue approve <T> -c <C> --override-must-fix --reason "<why>"` then `cw dev-queue requeue <T> -c <C> --stage finalize`. Who: orchestrator.
- **`review_not_converging`**: A clean-mode review stopped on `no_progress` or `oscillation`; the history comment on the ticket says which and lists the recurring findings. Read it and adjudicate via `/cw-followup`. A real defect goes back with `cw dev-queue requeue <T> -c <C> --stage impl --regress`. A `no_progress` stop is terminal until a commit lands: a same-tip `cw dev-queue requeue <T> -c <C>` only re-emits it. For an `oscillation` that is a false positive, run `cw review converge operator-settle <file> --ticket-id <T> -c <C> --reason "<why>"` (the payload is in the history comment; it records who and why), then `cw dev-queue requeue <T> -c <C>`. That releases the stop only when every recurring finding is settled; one left unsettled re-stops. Raising `review.max_cycles` or changing `convergence` is operator-only because it is a `clients.yaml` edit. A long review stage with a falling new-finding count is healthy. Who: orchestrator.
- **`review_blocked`**: In blocking mode, follow `show`'s `next:` and adjudicate the posted findings via `/cw-followup`. In clean mode (`blocker.details` says "clean-mode max_cycles backstop") the cap is on fix cycles. The operator raises `review.max_cycles` in `clients.yaml`, then `cw dev-queue requeue <T> -c <C>` re-reviews the same tip under the new cap, with no commit needed (it takes effect at the next spawn). If the cap was not raised the requeue re-emits the stop. A real defect still goes back with `cw dev-queue requeue <T> -c <C> --stage impl --regress`. Who: orchestrator.
- **`review_operator_actionable`**: Execute the `## Operator-Actionable Review Findings` checklist (ADR-0020). In clean mode the stop recorded the triggering finding(s), and the exit's `blocker.details` carries them as a ready-to-paste payload (`{"entries":[{"severity":"MUST_FIX","file":"N/A","summary":"<verbatim>"}]}`). If the checklist discharged a finding the reviewer would raise again, save that payload to a file and first run `cw review converge operator-settle <file> --ticket-id <T> -c <C> --reason "<why>"` (no other flag is needed; `N/A` is accepted as the file). Then run `cw dev-queue requeue <T> -c <C>`: the requeue itself clears the `stop_operator_action` stop and the review re-runs a full round on the same tip, and a settled finding does not stop it again. Without the settle, a re-raise of the same finding stops the review again. If `blocker.details` opens with `OPERATOR DECISION REQUIRED`, this is a decision contest (#2984), not a checklist: there is no `operator-settle` payload. Dismiss each contested finding with `cw review settle` (payload in the comment) or change course yourself, then `cw dev-queue requeue <T> -c <C>`. Who: orchestrator.
- **`codex_plan_artifact_missing` / `codex_plan_gate_failed`**: A codex PLAN run (#3060) returned no plan, or its plan failed a cw cross-check (`details` names the gate: `files_modified`, `scope_tier_line` or `scope_tier_match`). Neither is retry-eligible. Read `cw dev-queue show <T> -c <C>`, then `cw dev-queue requeue <T> -c <C>` to regenerate at the plan stage. A large codex plan is approved only with `cw dev-queue approve <T> -c <C>` (comment-path approval is not on the codex lane yet). Who: orchestrator.
- **`pr_already_terminal`**: A codex FINALIZE run (#3062) found the ticket's feature-branch PR already CLOSED, so there is nothing to ship; it is not retry-eligible and cw never reopens it. Read `cw dev-queue show <T> -c <C>` and the PR, decide whether the closure was intended, then either cancel the row with `cw dev-queue cancel <T> -c <C>` or reopen the PR and run `cw dev-queue requeue <T> -c <C> --stage finalize`. Who: orchestrator.
- **`merge_conflict_post_push`**: A codex FINALIZE run (#3062) found the branch conflicts with the default branch; cw never resolves it. Merge the default branch into the branch once and resolve the conflict (a merge, never a rebase or force-push), then run `cw dev-queue requeue <T> -c <C> --stage finalize`. Read `cw dev-queue show <T> -c <C>` first. Who: orchestrator.
- **`scope_tier_unresolvable`**: A codex FINALIZE run (#3062) could not resolve the scope tier from the plan and carried-through context, so cw would not guess past the Large-tier approval gate. Read `cw dev-queue show <T> -c <C>`, restore the plan (`.cw/plan.md` with its `**Scope tier:**` line) or fix the tier source, then run `cw dev-queue requeue <T> -c <C> --stage finalize`. Who: orchestrator.
- **`review_engine_modified`**: The Claude-native review stage parked because the branch touches the repo review engine skill or a path in its `guarded_paths`; the `## Blocking Review Findings` comment lists the touched paths. Inspect the head (the engine must not judge its own change), then run `cw review engine allow --ticket <T> --head-sha <sha> --reason "<why>" -c <C>` with the full 40-hex head, then `cw dev-queue requeue <T> -c <C>`. The allow covers that exact head only, so a later commit parks again and needs a new allow. If the change to the engine is not acceptable, send it back with `cw dev-queue requeue <T> -c <C> --stage impl --regress`. Who: orchestrator.
- **`review_confirm_must_fix`**: The clean-mode confirm round after a repo review engine pass raised a new MUST_FIX or a never-deferrable coverage/acceptance SHOULD_FIX (#3042); the engine's verdict is final, so cw charged no fix cycle and the `## Blocking Review Findings` comment lists the stop identities. To ship past them, run `cw dev-queue approve <T> -c <C> --override-must-fix --reason "<why>"` (it reads the parked round's saved verdict and converges the ledger), then `cw dev-queue requeue <T> -c <C> --stage finalize`. For a real defect, or a park the override refuses (no MUST_FIX, or a never-deferrable finding), run `cw dev-queue requeue <T> -c <C> --stage impl --regress`. `operator-settle` does not release it. Who: orchestrator.
- **`confirm_backend_unavailable`**: The independent confirmation round could not run. The reason means the backend is down, and only that: the cause in `blocker.details` is codex missing, an auth failure or another non-zero exit the backend itself reported, or a crash. Three such parks with the same cause at the same sha are the cap: the next failure with that cause escalates to an `agent_block` whose `details` say the backend is not recovering, so verify the backend before requeueing again and triage from `cw dev-queue show <T> -c <C>` once it escalates. That `agent_block` is outside the uncharged class, but it is charged only when the claim evidence shows no progress, so the real bound is the `blocked` park plus an explicit operator requeue; do not requeue repeatedly. A content-level failure on a healthy backend (a partial review, reviewers failing, unparseable output, findings a reviewer discarded unread) is NOT this row: it surfaces as `agent_block` with the cause in `details`, and the fix is that cause, not a backend restore. A slow or stalled confirm round is not this row either: no cw deadline kills it (ADR-0014), so a stall is a `cw-queue-peek` signal. The one hard bound is the harness's, not cw's: the confirm runs as a foreground Bash call at the 600 s tool cap, and a round that outlasts it surfaces as `agent_block`, not here, with `details` naming the ceiling and the last captured output. It means "diff too large for one foreground round", NOT "restore the backend": the backend may be healthy, so do not hunt for an outage, and a plain requeue re-runs the same round and re-spends codex quota. No automatic path requeues a REVIEW-stage `agent_block`, so each further round costs one explicit `cw dev-queue requeue <T> -c <C>`; escalate to the human, who decides on a smaller diff. This reason means the review did not finish, so nothing may ship. Read the cause from `cw dev-queue show <T> -c <C>`, restore the backend (installing or logging in to codex is a host-level action the human may have to do), then run `cw dev-queue requeue <T> -c <C>`. The ledger resumes at the confirm step without a new fix cycle. This park does not charge `unproductive_attempts` and consumes no review fix-cycle budget. The only way to skip the confirm round is for the operator to set `review.confirm_backend: none` in `clients.yaml`; never suggest that, and never `approve` past it. Who: orchestrator.
- **`attempt_cap_blocked`**: Run `cw dev-queue requeue <T> -c <C> --reset-attempts` once the cause of the failed attempts is read and fixed. Who: orchestrator. Never hand-edit the queue store to reset the counter.
- **salvage-parked row**: Run `cw dev-queue unblock <T> -c <C>`, or `cw dev-queue requeue <T> -c <C>` to re-run the stage. Who: orchestrator. The bound session's reap reason is `salvage_parked`.
- **`awaiting_operator` / `review_health_gate` / `review_artifacts_stale`**: Run `cw dev-queue requeue <T> -c <C>`, or `cw dev-queue drain --held -c <C>` to release held parks in bulk. Who: orchestrator. `drain` releases ALL held tickets of the client, not just this one; preview with `cw dev-queue drain --held -c <C> --dry-run`.
- **`branch_behind_main`**: The branch conflicts with the default branch. Merge the default branch into it once and resolve the conflict (a merge, never a rebase or force-push), then run `cw dev-queue requeue <T> -c <C>`. Who: orchestrator. Approve is refused here: it would ship a tree that cannot merge.
- **`ci_failing`**: Never approve or finalize past a red or conflicted head. Read `cw dev-queue show <T> -c <C>` and verify live PR state; `show`'s `next:` decides. By row status: COMPLETED shipped row with a red required check (paged `shipped_pr_checks_failed`): `cw dev-queue recover-red-pr <T> -c <C>`; it disarms auto-merge and regresses to impl with head-pinned feedback. Do not re-arm by hand. If `show` lists `--from-completed` instead (latch cleared, for example only an optional check is red), follow `show`. Parked row: `cw dev-queue requeue <T> -c <C> --stage impl --regress`, or `cw dev-queue requeue <T> -c <C> --stage impl --regress --review-feedback-file <file>` when you hold head-pinned evidence of the failure; skip any line `show` labels operator-only. RUNNING or PENDING row: `cw dev-queue wait <T> -c <C>`. A BEHIND PR keeps this state, and BEHIND alone needs no action (ADR-0022). The `auto_fix_ci` recipe is configuration-gated and does not always run; it may already have requeued the row. Re-read `show`; do not force `recover-red-pr` (rewiring is #2989). Do not create a sibling ticket/row. Who: orchestrator.
- **`merge_blocked`**: Never approve or finalize past a red or conflicted head. Read `cw dev-queue show <T> -c <C>` and verify live PR state; `show`'s `next:` decides. BEHIND alone has no merge-blocked attention or branch action (ADR-0022); handle CI failures and review requests through their own attention states. A clean branch is merged by GitHub or the merge queue. DIRTY is the conflict state. COMPLETED shipped row: if an opted-in repair recipe (`repair_changelog_conflict` or `repair_mechanical_conflict`) is armed, let it act and release its unarmed result with `cw dev-queue requeue <T> -c <C> --from-completed`. Otherwise resolve with one plain merge of the default branch (never a rebase or force-push), then `cw dev-queue requeue <T> -c <C> --from-completed`; finalize reuses the open PR, re-checks the tip (Step 4.0b / `delta-confirm`) and re-arms. Before that release, if the ticket worktree still exists, sync it first per the runbook "Release an unarmed repair" block (`git -C <worktree> fetch origin`, `status --porcelain`, `log --oneline <expected_sha>..HEAD`, then `reset --hard origin/<branch>` only if both are empty; finalize will not reset over local commits). Parked row: `cw dev-queue requeue <T> -c <C> --stage impl --regress`, or `cw dev-queue requeue <T> -c <C> --stage impl --regress --review-feedback-file <file>`. RUNNING or PENDING row: `cw dev-queue wait <T> -c <C>`. Do not create a sibling ticket/row. Who: orchestrator.
- **`merge_gate_blocked`**: Never approve or finalize past a red or conflicted head, or an open prior pipeline PR. Read `cw dev-queue show <T> -c <C>`: this row has no PR of its own; a prior pipeline PR (possibly another ticket's) blocks it. Identify that PR and verify its live PR state. Once it is clear, merge or close it, then run `cw dev-queue requeue <T> -c <C>`; this bypasses the park backoff, and a regress to impl is not the route. A red or conflicted blocking PR is routed by its own row per `ci_failing` / `merge_blocked`. RUNNING row: `cw dev-queue wait <T> -c <C>`. Do not create a sibling ticket/row. Who: orchestrator.
- **`stale_dispatch`**: Land or close the open PR an earlier run left for the ticket, then run `cw dev-queue requeue <T> -c <C>`. Who: orchestrator.
- **`gate_timeout`**: The finalize reuse-path quality gate was cut off by the foreground timeout (#3372); auto-merge was left as found, and the row is parked BLOCKED_ON_USER at finalize, not regressed. Confirm required CI is green at the PR head, then in the row's worktree, at that head, run the timed-out gate by hand with no time limit. If it passes on a clean tree, run `prep_pr_state.py gate-pass record <gate>` there, then `cw dev-queue requeue <T> -c <C>`. The recorded pass holds only at the same head and while the worktree exists; otherwise finalize re-runs the gate and may park again. Who: orchestrator.
- **`awaiting_operator_signoff` / `finalize_gate_held` / `scope_hint: large`**: Who: operator only. Notify the operator with the ticket, the gate and what `show` reports; do not release it yourself. These are gates the human opted into (ADR-0020). A large-by-size gate without `scope_hint: large` is not one of them; adjudicate that one as `plan_pending_approval`. When `approve` cannot take one of these gates, `show` lists a requeue labelled operator-only in its place. At the terminal stage that requeue releases the gate and ships; elsewhere (no bound session is at the gate) it re-runs the stage. It is still the operator's, so notify the operator and do not run it.
- **`blocked`**: With no bound session, run `cw dev-queue requeue <T> -c <C>` after reading the blocker (`cw session result <ref>` for a session that still exists). Who: orchestrator.
- **any other state**: Run `cw dev-queue show <T> -c <C>` and follow its `next:` line, which is the authority for every state not listed here. Who: orchestrator. That covers, for example, `scope_exceeded`, `forbidden_area`, `plan_unreviewable`, `plan_unsound`, `agent_block`, `tool_denied`, `empty_diff_blocked` and `merge_pending`. Escalate to the human only a genuine product or scope fork. One more `agent_block` shape: `unread_findings:` or `failed_role:` in `blocker.details` means the clean-mode engine refused to record a round because the reviewer lost findings (a mechanically rejected MUST_FIX, or a failure that discarded MUST_FIX or SHOULD_FIX claims) or because a reviewer role failed entirely, and it recorded nothing. The answer is a plain same-tip `cw dev-queue requeue <T> -c <C>` (the ledger is unchanged, so the review re-runs a full round with every role re-spawned), NOT `--regress`, and not an operator settle. If the same message comes back after a requeue, a reviewer is failing deterministically: read the cause in `details` and escalate to the human instead of requeueing again.

## Command semantics

- **Swing vs fan-out.** A *fan-out* is N independent tickets in N worktrees. A *swing* is one epic whose children share a design or a merge order, enqueued as ONE parent row whose body inlines the children under `## Children` (`/graduate-plan` swing track; RFC 0015 adds `--children`). Shared design or merge order means swing. A swing's plan stage parks on consolidated scans more than once; resolve with `cw dev-queue resolve`, and approve with `cw dev-queue approve` only on an approval-only park with no tracker comment after it, because a row-delivered resolution revokes a row approval across the revision it triggers.
- **Enqueue and placement.** `cw dev-queue add <T> -c <C> --lane <lane>` always passes `--lane`; without it the row lands in the `default` lane. `cw dev-queue move <T> -c <C> --to <lane>` fixes a wrong lane.
- **Read verbs.** `cw dev-queue tasks -c <C>` (all rows, NEXT column) and `cw dev-queue show <T> -c <C>` (one row with its legal `next:` commands) are the read verbs; `cw queue peek -c <C>` reads in-flight sessions; `cw session result <ref>` prints a session's `AUTO_DEV_RESULT` sentinel; `cw review history <T> -c <C>` (add `--json`) replays a clean-mode review round by round, so read it to tell converging from oscillating before adjudicating `review_not_converging`.
- **Readiness.** `cw preflight <T> -c <C>` runs the pre-flight checks for one ticket before dispatch.
- **Lane limits.** `cw lane set <C> <lane> max_parallel=N` changes a lane's concurrency. The settable keys are `max_parallel` and `attempt_ceiling` only; gate keys (`signoff`, `finalize_gate`), `reap_policy` and the guard toggles are refused (ADR-0020).
- **Client ceiling.** `cw config concurrency set ceiling=N -c <C>` sets a client's dispatch ceiling. With `-c` the only key is `ceiling`; every other key, gate keys included, is refused, and so is a run inside a dispatch worker.
- **Deferring an engine MUST_FIX (RFC 0017).** A repo review engine finding is never rejected; an engine MUST_FIX you accept for this run is deferred by its fingerprint in five steps. (1) Read `cw review converge status`, whose `stop.settle_payload` carries each engine finding's `severity`, `file`, `summary` and `fingerprint`, and the ticket's operator-actionable checklist. (2) Decide the finding is acceptable for this run. (3) Save the payload to a file and run `cw review converge operator-settle <file> --ticket-id <T> -c <C> --outcome defer --reason "<why>"`, keeping every entry's `fingerprint` verbatim. (4) Check the result: `unmatched` is empty and each entry emitted a `review.finding_settled` event with outcome `DEFERRED` and key `engine::<fingerprint>`. (5) Run `cw dev-queue requeue <T> -c <C>`. A `coverage.*` or `acceptance.*` finding cannot be deferred: the defer is inert and the finding re-opens each round until it is fixed. `operator-settle` is refused inside a headless worker.
- **Settling review findings.** `cw review settle <file> --ticket <T> --reason "<why>" -c <C>` records a settled finding on the row. `--ticket` and `--reason` are both required. The orchestrator runs it; it is refused inside a headless worker. It is also the `codex_must_fix_findings` route above. `cw review settle` writes the dev-queue row (the codex-lane route); the clean-mode Claude-native ledger reads its own settles, written by `cw review converge operator-settle`, which is refused inside a headless worker like `settle` and, unlike `settle`, can settle a finding with no file anchor (`file: "N/A"`) but only an identity the ledger has already recorded (an unmatched one exits 1 with a nearest-match hint, so nothing is settled pre-emptively).
- **Binding constraints.** `cw review constrain <T> --file <path> -c <C>` records a binding constraint (for example "do not add `foo_bar`") on the row. The codex review prompt and the codex fix loop read it from the row on every tracker, independent of any comment or login; the fix loop parks a cycle that introduces what it forbids. Write the text with the Write tool first. The printed stdout block is only a mirror to post with your tracker's own tool. Constraints are append-only (retraction is tracked in #2968); check them with `cw dev-queue tasks --json -c <C>`. The orchestrator runs it; it is refused inside a headless worker.
- **Interactive runs on a clean-mode client.** An interactive `/auto-dev` or `/auto-dev-review` on a client configured `review.convergence: clean` refuses with a dispatch message instead of falling back to `blocking`, so enqueue the ticket with `cw dev-queue add <T> -c <C> --lane <lane>` and let the queue dispatch it. A headless run without a ticket id (a bare headless spawn, which writes no ticket id) is refused the same way, with a `blocked` / `agent_block` sentinel whose `details` carry that instruction.
- **Waiting.** `cw dev-queue wait <T>... -c <C>` takes positional tickets; several tickets need `--any` (without it exactly one ticket is allowed), which returns on the first ticket to reach an exit state. `--stuck-after-minutes N` (default 15) sets the stuck threshold and `--timeout` defaults to 6 hours (`0` = no limit). It is one-shot, not a watch: on a row that is already parked or terminal it returns on the first poll. Exit codes: 0 shipped or no_op; 1 scope_exceeded, forbidden_area, FAILED or CANCELLED; 2 blocked, merge_pending, ambiguities_pending_resolution, premises_pending_verification or BLOCKED_ON_USER; 3 ATTENTION; `exit 4` human gate (operator signoff, finalize hold, `scope_hint: large`); `exit 5` stuck (a pending blocker that will not clear on its own, or an approval result dispatch has not routed); 124 hard timeout. Run it as a background task, for sequencing only.
- **Watching.** An orchestrator started with `cw orchestrator-start` gets `cw-operator` pushes (`<channel source="cw-operator">`) through a per-session `--mcp-config` file and needs no watch Monitor; it prints a stderr warning at launch when `cw queue-channel serve` is not reachable, and then it arms the Monitor below like any other session. A session started any other way keeps the watch Monitor. `cw orchestrate watch -c <C>` is the one standing attention stream. Arm it once per sprint under one Monitor with `timeout_ms: 1800000` and re-arm only when it expires; the saved position resumes, so nothing is replayed or lost. It prints nothing while everything is healthy. The first stdout line is the resolved scope: check it for `lanes=`. A second watch on the same scope needs `--force`, and only after confirming no watcher is alive. Flags: `--lane`, `--ticket`, `--all-lanes`, `--since`, `--stuck-after-minutes`, `--force`. Pass `--all-lanes` unless you are deliberately scoping: the default scope is your focus-pointer lane.

- **Posting tracker comments.** A comment an orchestrator session posts through the tracker's own write op (`gh issue comment`, `gh pr comment`, Linear `create_comment` or any tracker MCP) lands under the operator's account, so it must end with the marker line `<!-- cw-agent-authored -->` on its own line after a blank line; otherwise the *Comment provenance rule* in `.claude/commands/auto-dev.md` reads it as typed by the operator. Prefer `cw post-comment <T> --body-file <path> -c <C>`: it appends the marker itself. Never post operator-voice text unmarked, and never relay an operator decision unmarked: the binding record of an operator decision is the row (`cw dev-queue resolve`), and a relayed copy may be posted only marked (the relay block `cw dev-queue resolve` prints already ends with the marker). Mirrors that cw prints (`cw dev-queue resolve`, `cw review constrain`) already carry the marker. There are two deliberate exceptions: the `<!-- auto-dev-preflight-resolutions -->` comment that `/harden-ticket` posts under the operator's standing authorization, and the `marker.md` mirror that `cw review settle` prints (a machine-parsed disposition block that must open the comment body unedited; the row is authoritative; see `/cw-followup`). A comment whose text says it was authored or relayed by an orchestrator is read as agent analysis whether marked or not.

## Known cw hazards

- Never edit `~/.local/share/cw/dev_queue.json` with a dispatch loop alive: a tick's read-modify-write silently drops the edit. Use `cw dev-queue requeue <T> -c <C> --reset-attempts` instead (docs/dispatch-runbook.md).
- Close the session before removing its row: `cw spawn close --confirmed-dead <id>` first, then `cw dev-queue remove <T> -c <C>`; reversed, they race the dispatcher (#317).
- After upgrading cw, restart `cw dev-queue serve` before using `cw dev-queue resolve` or `cw review constrain`: an older loop rewrites the queue without the resolutions ledger or the constraints list and erases recorded answers and constraints (#2702, #2964). A stale loop is now flagged by `cw doctor` check `dispatch-loop-code` and by a stderr warning from `resolve`, `approve` and `constrain` (#2729).
- `cw review settle`, `cw review constrain`, `cw dev-queue resolve` and `cw dev-queue approve` are refused inside a headless dispatch worker; the orchestrator runs them (#2701, #2964, #2702, #2776).
- `cw dev-queue requeue` on a row that is already PENDING is a no-op, and `--reset-attempts` is not applied there (src/cw/dev_queue/requeue.py, #2692).
- `cw dev-queue add` against a row that is pending, running or parked is refused; release a parked row with `resolve`, `requeue` or `approve` (src/cw/dev_queue/crud.py, #1653).
- Do not start `cw dev-queue run` when a dispatch loop is already live; check `pgrep -f 'cw dev-queue (run|serve)'` first. A manual tick races the live loop and can phantom-sweep in-flight sessions (#317).

## Monitor and rescue

Skills compose over the primitives; prefer them for in-flight work.

- `/orchestrate-sprint`: the conductor loop for a sprint, built on this map.
- `/cw-queue-peek`: WAIT / PEEK / STOP per RUNNING session, at a checkpoint.
- `/cw-fanout`: enqueue and watch a wave in one motion.
- `/cw-session-watch`: did one session finish, and with what status.
- `/cw-validate-result`: forensic read of what a session shipped or blocked on.
- `/cw-followup`: act on a finished session's sentinel.
- A wedged session: verify death first (absent from
  `~/.claude/daemon/roster.json`, transcript flat, no live process), then
  `cw spawn close --confirmed-dead <id>` (flag before the id). Prune merged
  worktrees with `cw worktree gc --apply`.

## Do NOT

- Hand-roll `claude --bg` spawns when a cw command does it.
- Use `ScheduleWakeup`, sleep or cron polling, or `/loop` babysitting to watch
  work. The `cw orchestrate watch` Monitor is push; silence means healthy.
- Do not run `gh pr create` or `gh pr merge` for normal pipeline-owned
  headless shipping; the pipeline ships with auto-merge itself. Preserve the
  documented `attach_ui_evidence` and `pr.auto_merge: false` recovery paths,
  where the orchestrator may run `gh pr merge` after the required recovery
  work.
- Parse `cw list` or `cw watch` output: the text columns are unstable. Use
  `cw dev-queue show <T> -c <C>`, `cw dev-queue tasks -c <C> --json`,
  `cw session result <ref>` or `cw queue peek -c <C> --json`.
- Guess sentinel semantics. The `AUTO_DEV_RESULT` schema is the contract
  (`docs/headless-contract.md`); `cw result validate -` checks a payload.

If you catch yourself typing `claude --bg`, a polling loop, a `gh pr create`,
or a manual `cw dev-queue run` tick to coordinate autonomous work, that IS the
signal: stop and check whether a cw command, or a loop that is already
running, already owns that step.
